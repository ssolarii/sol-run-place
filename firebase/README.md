# Visitor submissions

Target Firebase project: `homepage-ef7cd`, Firestore `(default)` database.
Firebase Anonymous Authentication and the reviewed rules are enabled in the
live project (verified 2026-10-27). The site
signs a visitor in anonymously and retains that Firebase Auth session locally.
There is no client-side admin role or inbox. Sol reads private submissions and
moderates guestbook entries in the Firebase console using project IAM access.

## Client contract

Create a Firestore auto-ID document and its limiter together in one `writeBatch`:

| Path | Required fields | Optional fields |
| --- | --- | --- |
| `privateMessages/{autoId}` | `senderId: auth.currentUser.uid`, `body: string` (1–2000 characters, containing non-whitespace), `createdAt: serverTimestamp()` | `displayName: string` (at most 60 characters) |
| `guestbook/{autoId}` | `senderId: auth.currentUser.uid`, `body: string` (1–500 characters, containing non-whitespace), `createdAt: serverTimestamp()`, `status: "pending"` | `displayName: string` (at most 60 characters) |
| `submissionLimits/{uid}` | `lastSentAt: serverTimestamp()`, `entryId: autoId`, `kind: "private"` or `"guestbook"` | None |

All other fields are rejected. Document IDs must be 20 alphanumeric characters,
as generated by `doc(collection(db, collectionName))`. Omit a blank display name
or send an empty string; do not send `null` or `undefined`. Trim the body in the
UI. Submit plain text and render public content with `textContent`, never HTML.

```js
const uid = auth.currentUser.uid;
const kind = 'private'; // or 'guestbook'
const entry = doc(collection(db, kind === 'private' ? 'privateMessages' : 'guestbook'));
const batch = writeBatch(db);
batch.set(entry, {
  senderId: uid,
  body: body.trim(),
  createdAt: serverTimestamp(),
  ...(displayName.trim() ? { displayName: displayName.trim() } : {}),
  ...(kind === 'guestbook' ? { status: 'pending' } : {})
});
batch.set(doc(db, 'submissionLimits', uid), {
  lastSentAt: serverTimestamp(), entryId: entry.id, kind
});
await batch.commit();
```

Show success only after the commit resolves. A private entry cannot be read back,
even by its sender. A guestbook entry is hidden until moderation. The client may
read its own limiter with `getDoc` to display a cooldown; limiter lists and other
visitors' limiters are denied. The same UID must wait at least 60 seconds between
any two submissions, across both forms. The server enforces the cooldown and
timestamps; a browser timer only explains the wait.

Public guestbook loading (no sign-in required):

```js
getDocs(query(collection(db, 'guestbook'),
  where('status', '==', 'published'),
  orderBy('createdAt', 'desc'),
  limit(50)));
```

The filter and a limit of 50 or less are mandatory. Published entries are also
readable individually. All fields of a published guestbook document, including
its sender's anonymous UID, are public. Keep private content exclusively in
`privateMessages`. Visitors cannot edit or delete submissions, change moderation
status, or list pending entries. In the Firebase console Sol can change
`guestbook/{id}.status` to `published` or `rejected`, or delete unwanted entries.
No page client can read any private message. Console/IAM access bypasses these
client security rules.

## Reading and approving messages

Private inbox: [Firebase private messages](https://console.firebase.google.com/u/0/project/homepage-ef7cd/firestore/databases/-default-/data/~2FprivateMessages).
Open a document to read its `body`, optional `displayName` and `createdAt`.
The visitor site has no inbox or private read permission.

Guestbook queue: [Firebase guestbook](https://console.firebase.google.com/u/0/project/homepage-ef7cd/firestore/databases/-default-/data/~2Fguestbook).
Review the text, then change `status` from `pending` to `published` to show it
on the site. Use `rejected` to keep it hidden. Publishing makes the entire
guestbook document public; do not copy private messages into this collection.
Labelled website setup-check entries can be left unpublished or deleted by Sol.

## Browser client

`submissions-client.mjs` uses Firestore Lite with no offline write queue or
private-body persistence. The factory is idle until a public read or send.
Anonymous Auth loads only on send and waits for restored identity. Both forms
share one pending-send lock and cooldown. A failed commit acknowledgement is
reported as uncertain; the client never automatically resends.

The self-hosted split bundle is generated into
`../world-draft/assets/submissions/`. SDK version is pinned at 13.0.0. Build
output has no external module imports or embedded account credentials.

```sh
npm ci --ignore-scripts
npm run build:client
npm run test:client
npm run test:client:emulator
```

Verified: 15 client behavior tests and two actual Lite emulator integration
tests passed. Browser form checks also verified real private delivery,
guestbook pending delivery, cross-form cooldown, whitespace rejection, offline
text preservation and no false success. These checks created labelled private
and pending guestbook setup records; none was published.

## Deployment inputs

Review these files before deployment. This folder contains no Hosting config,
credentials, or service account key. From this directory, using an authenticated
Firebase CLI with permission on `homepage-ef7cd`:

```sh
firebase deploy --project homepage-ef7cd --only firestore:rules,firestore:indexes
```

The `firebase.json` references `firestore.rules` and `firestore.indexes.json`.
The composite index supports the public query above; wait for index creation to
finish before verifying that query in production. Rules deployed by the CLI
replace the database's existing rules: review any unrelated existing collection
access before deployment. These rules deny every unlisted collection/path.

## Local verification

The test suite exercises actual Firestore rules in the emulator with the web
SDK and mocked Firebase Auth identities; it does not contact production.
Dependencies are pinned in `package-lock.json`. Node 20+ and Java 17+ are needed
for the pinned Firebase CLI 14.27.0 and Firestore emulator 1.19.8. Newer CLI
versions may require Java 21.

```sh
npm ci --ignore-scripts
npm test
```

The emulator uses `127.0.0.1:8087` and the isolated demo project
`demo-sol-submissions`. A production browser/Auth integration check and deployed
composite-index check are separate from these emulator security tests.

Verified locally on 2026-10-27: the saved package's `npm test` completed with
25 tests passing, zero failures, using Node 24.22.1, Java 17.0.20, and the pinned
tools above. Tests cover valid batches, denied unauthenticated/spoofed writes,
private read/list denial across identities, pending/public visibility, query
limits, cooldowns across both forms, malformed data, immutable entries, and
attempts to reuse a limiter for several entries. The initial deny-all baseline
failed the two valid-submission tests before implementing the rules.

## Limits

Anonymous identity is not proof of a unique person. Clearing browser data or
creating fresh anonymous accounts bypasses a per-UID cooldown. These rules are
not an IP rate limiter, CAPTCHA, or a guarantee against automated abuse.
Submissions use two document writes, and rule lookups/public queries consume
Firestore quota. On the no-billing Spark plan the service can stop working when
free quotas are exhausted. Use the Firebase console to review/delete retained
submissions and monitor usage. No billing service, Cloud Function, self-hosted
server, Supabase service, or custom admin login is required by this design.
